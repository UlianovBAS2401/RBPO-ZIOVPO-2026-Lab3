Лабораторная №3  
   
 Небольшой сервис на Java и Spring Boot для учёта коммуналки (воды, электричества, газа), снятия показаний и расчёта квитанций. Во второй лабе всё было в памяти, теперь подключили нормальную базу PostgreSQL.  
   
 Сущности:  
User - абонент (ФИО, почта, телефон).  
Premises - помещение/квартира (адрес, площадь, чей объект).  
Meter - счётчик (тип ресурса, серийный номер, тариф за единицу, статус). Привязан к помещению.  
MeterReading - показание счётчика за конкретный месяц. Привязано к счётчику.  
UtilityCharge - квитанция/начисление (период, объём, сумма к оплате, статус оплаты).  
 Ограничения в базе (Constraints)  
Почта пользователя (email) и номер счётчика (serial_number) уникальны.  
Нельзя внести два показания для одного и того же счётчика за один и тот же месяц (UNIQUE(meter_id, period)).  
Проверки на числа: площадь area > 0, тариф unit_rate > 0, показания reading_value >= 0, объём и сумма >= 0.  
   
Статусы строго фиксированы:  
 у счётчика: ACTIVE, INACTIVE, FAULTY  
 у показания: PENDING, VERIFIED, REJECTED  
 у квитанции: CALCULATED, PAID, CANCELLED  
   
Внешние ключи с защитой: нельзя удалить пользователя, если на него оформлена квартира (RESTRICT).  
 Что умеет сервис (Бизнес-логика)  
1. Базовый CRUD по всем 5 сущностям (создание, получение, изменение, удаление).Верификация показаний (POST /api/meter-readings/{id}/verify) — проверка показаний контролёром. Сервис проверяет, чтобы новое показание не было меньше предыдущего.  
2. Авторасчёт начислений (POST /api/utility-charges/calculate) — передаём счётчик и месяц, система сама считает разницу с прошлым показанием, умножает на тариф и формирует квитанцию.  
3. Оплата квитанции (POST /api/utility-charges/{id}/pay) — переводит квитанцию в статус PAID (повторно оплатить уже оплаченную не даёт).
